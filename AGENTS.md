# AGENTS.md

This is the AWS SDK for Java 2.x: service clients generated at build time from AWS service models, plus the hand-written core runtime, HTTP clients, and high-level libraries they run on. The files under `docs/guidelines/` add depth, and each section says when to read one.

## Build and test commands

The Maven reactor has about 500 modules. Run Maven through `./mvnw` from the repository root, scoped with `-pl` to the modules you changed.

| Step | Command |
|---|---|
| Build the module and the modules it depends on | `./mvnw -pl <module> -am -DskipTests -Dmaven.javadoc.skip=true -Dspotbugs.skip=true install` |
| Run the module's whole unit test suite, without `-am` | `./mvnw -pl <module> -Dmaven.javadoc.skip=true -Dspotbugs.skip=true test` |
| Run one test class while iterating | `./mvnw -pl <module> -Dtest=<TestClass> -DfailIfNoTests=true -Dmaven.javadoc.skip=true -Dspotbugs.skip=true test` |
| Run SpotBugs on the module | `./mvnw -pl <module> -Dspotbugs.skip=false process-classes` |

- Build with `install`, not `compile` or `test`: modules depend on shaded jars that exist only after `package`. After editing a module upstream of the one you test, rerun the build step before testing.
- Finish with the whole-module test run. A single-class run misses tests that reach your code through other classes.
- `install` is the step that runs japicmp, so run the build step after your last edit. A passing `test` run says nothing about API compatibility.
- Checkstyle runs in `validate`, so every command above runs it. There is no auto-formatter.
- If a `test` run cannot resolve `bom-internal`, run the build step with `-pl bom-internal` first.
- If the build fails with `Attempted to clobber existing file`, a `target/` directory holds stale generated sources, for example after switching branches. Add `clean` before `install` and rerun.
- After a `utils` or `core/*` change, also run the unit test suites of the modules that call the changed code.
- Unit tests in `services/*`, `services-custom/*`, and `test/*` build clients that need a region and credentials. Nothing calls AWS, so placeholders work: prefix the test command with `AWS_REGION=us-west-2 AWS_ACCESS_KEY_ID=akid AWS_SECRET_ACCESS_KEY=skid`. Leave the two credential variables off any run that includes `core/auth`, whose tests expect them unset.
- Do not verify a change with `-P quick`: it skips unit tests, Checkstyle, and japicmp and still reports `BUILD SUCCESS`. Do not run `install` or `test` from the root without `-pl`.
- The commands in `README.md` and `CONTRIBUTING.md` build the whole tree, skip checks with `-P quick`, or use `mvn` instead of `./mvnw`. Use the ones in this section.

## Generated code

Files under any `target/generated-sources/` directory are regenerated by every build, so an edit there is lost. Never edit them. Change what generates them:

- Service clients and models: the generator in `codegen/` turns each `services/<service>` module's `src/main/resources/codegen-resources/` files into its `target/generated-sources/sdk`. Do not edit any file in those service `codegen-resources/` directories except `customization.config`: release automation replaces the others with each service's published model.
- `customization.config` is maintained by hand and is the place to adjust one service's generated code. The options it can set are the fields of `codegen/src/main/java/software/amazon/awssdk/codegen/model/config/customization/CustomizationConfig.java`.
- Hand-written code that a generated client calls, such as the execution interceptors listed under `interceptors` in `customization.config`, lives in the module's `src/main/java`, usually in an `internal` package. Edit it directly.
- `core/regions` and `core/aws-core`: the generators in `codegen-lite/`. Their inputs `core/regions/src/main/resources/software/amazon/awssdk/regions/internal/region/endpoints.json` and `core/aws-core/src/main/resources/software/amazon/awssdk/awscore/internal/defaults/sdk-default-configuration.json` are replaced by release automation; do not edit them.
- `core/sdk-core`: the `VersionInfo.java.vm` template in that module.

## Code generator

A change in `codegen/` changes every service client. To fix code that every service generates, change the generator rather than one service. Before changing `codegen/`, read `docs/guidelines/code-generation-guidelines.md`.

- JavaPoet specs are under `codegen/src/main/java/software/amazon/awssdk/codegen/poet/`. A new generated class gets `@Generated` from `PoetUtils.generatedAnnotation()`.
- Test the behavior of generated clients with a functional test in `test/codegen-generated-classes-test`, which generates clients from the test models in its `src/main/resources/codegen-resources/`. Those models are maintained by hand, so edit or add them as the test needs. Marshalling tests for each protocol live in `test/protocol-tests`.
- To verify a change, build `codegen` and run its unit test suite (when generated output changes on purpose, update the expected-output fixtures its tests compare against), then build and test one affected `services/<service>` module and `test/codegen-generated-classes-test` with the placeholder region and credentials above.

## Code conventions

- Put new types in an `internal` package and annotate them `@SdkInternalApi`, and make a fix in `internal` code when it can live there. Add `@SdkPublicApi` or `@SdkProtectedApi` types only when the change cannot be made without them.
- Use the SDK's utilities instead of a new dependency or a hand-written version: `JsonNodeParser` (`core/json-utils`) for JSON, `Lazy` and `CachedSupplier` (`utils`) for lazy and TTL-cached values, `Validate` for argument checks, and `ToString` for `toString()`.
- Argument and configuration checks use `Validate`, which throws `IllegalArgumentException` or `NullPointerException`. Failures at request time throw `SdkClientException` or another `SdkException` subtype. Do not throw checked exceptions from public APIs, and do not catch an exception only to rethrow the same type. Messages say what went wrong and how to fix it. Before adding or changing exception handling or a public value class, read `docs/guidelines/aws-sdk-java-v2-general.md`.
- Log through `software.amazon.awssdk.utils.Logger` (`private static final Logger logger = Logger.loggerFor(MyClass.class);`), not SLF4J directly, unless Checkstyle bans it in that module; then use the logger that neighboring code uses. Do not log at WARN or ERROR an error that is also thrown to the caller. Before adding or changing a log statement, read `docs/guidelines/logging-guidelines.md`.
- Do not use `Optional` for parameters, fields, values that are never null, or getters on generated model classes. Return it only when a caller could not otherwise tell that the result may be absent.
- Public value classes implement `equals`, `hashCode`, and `toString` over all fields and have an `EqualsVerifier` test.
- `CompletableFuture`: never drop a future that can fail, and handle its failure with `exceptionally`, `handle`, or `whenComplete`. Do not call `join()` or `get()` inside a future chain. Pass an executor to every `*Async` method. Propagate cancellation with `CompletableFutureUtils.forwardExceptionTo`, and where a sync path must wait, use `CompletableFutureUtils.joinLikeSync`. Before changing code that uses `CompletableFuture`, read `docs/guidelines/async-programming-guidelines.md`.
- Reactive Streams: build on `SimplePublisher`, `ByteBufferStoringSubscriber`, and `SdkPublisher` instead of writing a `Publisher` or `Subscriber` from scratch. A change to any `Publisher` or `Subscriber` implementation needs a Reactive Streams TCK test named `<ClassName>TckTest` in the same package, like `utils/src/test/java/software/amazon/awssdk/utils/async/SimplePublisherTckTest.java`. Before changing a `Publisher` or `Subscriber`, read `docs/guidelines/reactive-streams-guidelines.md`.
- Use code comments sparingly. Add one only for a reason the code cannot show, such as a hidden constraint, a subtle invariant, or a workaround for a specific bug, and never to restate what the code does. Javadoc on public API is separate and follows the next rule.
- Every public API has Javadoc: a one-sentence summary first, in third person ("Returns the..."), and `<p>` with no closing tag at the start of each later paragraph. Before adding or changing public or protected API, read `docs/guidelines/javadoc-guidelines.md`.

## API compatibility

- Never remove, rename, or narrow a public or protected member, or change its signature. Add the new form, keep the old one, and mark it `@Deprecated` with a `@deprecated` Javadoc tag that links the replacement. On `install`, japicmp fails the build for binary-incompatible or source-incompatible changes in the modules it checks; `*.internal.*` packages are exempt.
- Older generated clients call `@SdkProtectedApi` members, so keep them as backward compatible as public API even though customers do not call them directly.

## Testing instructions

- Every behavior change comes with a new or updated unit test in the changed module's `src/test/java`. Before adding or changing a test, read `docs/guidelines/testing-guidelines.md`.
- Use JUnit 5 with AssertJ and Mockito, and WireMock to stub HTTP responses, as `services-custom/s3-transfer-manager/src/test/java/software/amazon/awssdk/transfer/s3/internal/DownloadDirectoryRefusedKeyWireMockTest.java` does.
- Name test methods `methodToTest_when_expectedBehavior`, for example `close_withCustomExecutor_shouldNotCloseCustomExecutor`, and name a class that tests one class `<ClassName>Test`.
- On an error path, assert the exception type and part of its message.
- Keep test-only constructors and methods package-private, and annotate them `@SdkTestInternalApi` (`core/annotations`).
- Prefer unit and functional tests that mock dependencies with Mockito or stub HTTP responses with WireMock over integration tests (`src/it/java`, `*IntegrationTest`), which call real AWS services.

## Security considerations

- Never log, or put in `toString()` or an exception message, credentials, HTTP header values, or members modeled as sensitive.
- Tests use placeholder credentials such as `akid` and `skid`. Never put real credentials in tests or test resources.

## Pull request instructions

- Before opening a pull request, run the build step and the whole-module test run for every module you changed.
- A pull request sourced by AI tools must be reviewed by a person before it is opened.
- Add a changelog entry, as described next.

### Changelog entry

Every change customers can observe needs an entry in `.changes/next-release/`, including a change made only in `customization.config`. CI enforces this for non-test Java files. Create the entry with `scripts/new-change`, which writes the JSON file and stages it with `git add`. Choose the values first:

- `-c` (category): the changed component's own category, as existing entries in `.changes/` name it. Use the library name for a library, such as `S3 Transfer Manager`, `Amazon DynamoDB Enhanced Client`, `Netty NIO HTTP Client`, `Apache HTTP Client`, or `AWS CRT HTTP Client`; the service name for a service module, such as `Amazon S3` or `Amazon DynamoDB`; and `AWS SDK for Java v2` only for core, `utils`, and codegen changes.
- `-t` (type): one of `bugfix`, `feature`, `perf-improvement`, `deprecation`, `removal`, `documentation`.
- `-d` (description): the user-visible behavior change, with no ticket numbers or internal references.

```sh
EDITOR=true python3 scripts/new-change -t <type> -c "<category>" -d "<description>"
```

SDK maintainers leave `-u` out. An external contributor may pass their own GitHub username with `-u`; never guess one. Without `-u` the script opens an editor, and `EDITOR=true` makes that a no-op. The script reads `VISUAL` before `EDITOR`, so if `VISUAL` is set, unset it or set it to `true` as well.
