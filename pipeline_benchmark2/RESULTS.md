# V2-on-smithy-java: measured cost

Raw data: `pipeline_benchmark2/paired/20260904-2140/` (manifest, `results.csv`, per-run logs,
generated `summary.md`). This file is the interpretation; the numbers below are all reproducible from
that directory and the two archived jars.

## What ran

| | |
|---|---|
| Host | `dev-dsk-alexwoo-2b-ee3cc828`, Intel Xeon Platinum 8124M @ 3.0 GHz, 8 logical cores, JDK 21.0.9 |
| Baseline jar | `bridge-baseline-published-2.46.10-dirty.jar` — **published** v2 2.46.10 from Maven Central |
| Bridge jar | `bridge-bridge-ee9a74f69db-dirty.jar` — this branch's SDK, v2 API on the smithy-java pipeline |
| Config | 50 000 measured ops, 30 000 warmup (quiesce mode), 4 paired reps, concurrency 1, client pinned to CPUs 0–1, mock server to 4–6 |
| Runs | 96, zero failures, `server_requests == iterations` on all 96, server never saturated |

Both jars carry the **same harness commit**, so the SDK is the only difference between arms. Arms
alternate within each rep and the order reverses on even reps.

Four measures were recorded (app CPU µs/op, mean latency, wall µs/op, process CPU). They agree
throughout; app CPU and latency are quoted below.

## Headline: the bridged pipeline is faster than stock v2

app CPU µs/op (percentages vs stock v2):

| arm | small-get | small-put | batch-get | batch-put |
|---|---:|---:|---:|---:|
| stock v2 2.46.10 | 136.6 | 132.3 | 580.3 | 749.6 |
| **v2 API on smithy pipeline** | **92.3 (−32%)** | **87.8 (−34%)** | **469.8 (−19%)** | **424.6 (−43%)** |
| same, bridges stripped (`stripAll`) | 82.1 (−40%) | 79.5 (−40%) | 464.4 (−20%) | 396.9 (−47%) |
| native smithy-java client | 60.0 (−56%) | 59.7 (−55%) | 319.9 (−45%) | 335.2 (−55%) |

mean latency µs:

| arm | small-get | small-put | batch-get | batch-put |
|---|---:|---:|---:|---:|
| stock v2 2.46.10 | 174.7 | 170.6 | 634.9 | 793.5 |
| **v2 API on smithy pipeline** | **127.9 (−27%)** | **124.8 (−27%)** | **522.4 (−18%)** | **461.7 (−42%)** |
| same, bridges stripped | 117.3 (−33%) | 115.9 (−32%) | 510.8 (−20%) | 436.1 (−45%) |
| native smithy-java client | 94.9 (−46%) | 100.4 (−41%) | 359.6 (−43%) | 381.2 (−52%) |

This is the opposite sign from the earlier full-bridge POC, which was 2–3× *slower* than v2. Bridging
a minimal set of components — HTTP transport, credentials, endpoint rules, retry strategy,
interceptors — and letting smithy-java own serialization, signing and the call pipeline lands the v2
API meaningfully ahead of v2's own pipeline.

These numbers **predate the inert-interceptor filter** (see *Acting on it*, below), which took another
7–8% off the bridged row on the small scenarios. They are left as measured rather than adjusted, since
the −32%/−34% is the conservative statement and re-running the full four-arm cross-jar collection is
the honest way to update it.

## Decomposition of the remaining gap to native smithy

Reading the latency column for `small-get`: 175 → 128 → 117 → 95 µs.

| step | cost | what it is |
|---|---:|---|
| stock v2 → bridged v2 | −47 µs | what v2's own pipeline costs over smithy's |
| bridged → bridges stripped | 11 µs (8% of the bridged client) | the **bridging tax**: V2 endpoint rules engine per attempt, `SdkRetryStrategy` wrapper, error enricher (2.1, 3.1, 5.1 in `compatability_issues.md`) |
| stripped → native smithy | 22 µs (19% of stock v2) | the part that cannot be stripped: v2 model objects, `SdkPojoSerializer`/`SdkPojoDeserializer`, the generated v2 client veneer |

So of the ~80 µs between stock v2 and native smithy on a small op, roughly **11 µs is component
bridging and 22 µs is the v2 API/model surface** — the veneer is twice the cost of the bridges. With the
inert-interceptor filter in (measured after this collection) the bridging half shrinks to roughly 5–6%
of the bridged client, so the veneer is closer to three times the cost of the bridges and is now clearly
where the remaining gap lives.

The batch scenarios split asymmetrically and it is worth chasing: batch-**put** (large request,
serialization-heavy) is −43%, while batch-**get** (large response, deserialization-heavy) is only
−19%, and native smithy beats the bridge by 45% on batch-get versus 27% on batch-put. That points at
`SdkPojoDeserializer`/`BridgeStruct` — building v2 model objects out of smithy's deserializer — as the
most expensive bridge on large payloads. An allocation profile would confirm it.

## Which bridge costs what

Raw data: `pipeline_benchmark2/components/20260904-2313/` (48 runs, zero failures, `summary.md`
generated by `analysis/scripts/client_sweep_summary.py`). One jar, six clients, 4 interleaved reps,
60 000 ops each — so the *client* is the only difference, and each arm removes exactly one bridge.

app CPU µs/op against the fully-bridged `v2-sync` client on the same jar:

| arm removed | small-get | small-put | paired wins |
|---|---:|---:|---:|
| interceptor bridge | −5.9% | −8.4% | 4/4 |
| endpoint bridge (V2 rules engine) | −4.0% | −5.1% | 4/4 |
| retry strategy wrapper | −0.4% | −0.3% | 3/4, 2/4 |
| error enricher | +0.1% | −0.4% | 3/4, 2/4 |
| **all four (`stripAll`)** | **−13.7%** | **−13.8%** | 4/4 |

Two things stand out.

**The interceptor bridge was supposed to be inert, and it was the most expensive one.** The bridge
installs `V2InterceptorBridge` only when the resolved interceptor list is non-empty, and DynamoDB
contributes no classpath interceptors — but `AwsDefaultClientBuilder.awsInterceptors()` adds three to
*every* AWS client (`HelpfulUnknownHostExceptionInterceptor`, `EventStreamInitialRequestInterceptor`,
`TraceIdExecutionInterceptor`), none of which the bridge treats as replaced. So every client pays
per-attempt v2 `Context`/`ExecutionAttributes` construction at four hook points to run three
interceptors that no-op on this workload — and one of them (`HelpfulUnknownHostExceptionInterceptor`)
only implements `modifyException`, a hook this bridge never invokes, so it cannot have an effect at
all. Not all of the 5.9% is bridging tax: stock v2 runs those three interceptors too.

That one is now fixed, and the fix recovers all of it — see the next section.

**Retry and error bridging are free on the success path**, both inside the noise floor with split win
counts. That is the expected shape — the error enricher only works on errors, and the retry wrapper
only on a retried attempt — but it means the "both arms" retry question cannot be answered from a
benchmark that never fails a call. It needs a fault-injecting scenario.

The four components sum to 10.4% against a measured 13.7% for `stripAll`, so ~3% is superadditive:
plausibly the endpoint memo and the interceptor path keeping each other's objects alive, but not
resolved here.

Two caveats specific to this collection. `stripAll` reads −10.5% on *latency* here versus the 8% quoted
in the decomposition above — the two come from different collections and different measures (app CPU
vs latency, within-jar vs cross-jar), and 8–13% is the honest range for the bridging tax rather than
either endpoint being exact. And 33 of these 48 runs were not steady-state, on every arm including the
reference; raising `--warmup-max-seconds` to 120 did not fix it because warmup was already reporting
settled (see caveat 1). Since the bias applies to all six arms in the same collection and the paired
spreads are ±1.2–3.7%, it does not explain a 4/4-win effect, but it is why these percentages are
quoted to one decimal and not defended below ~2%.

## Acting on it: dropping the inert interceptors

Raw data: `pipeline_benchmark2/inertfilter/20260904-2355/` (32 runs, zero failures, `summary.md`).
Same shape of collection, one jar, four clients, 4 interleaved reps, 60 000 ops.

`V2ConfigTranslator.inert()` now drops an interceptor the bridge cannot usefully run: generally, any
interceptor overriding none of the six hooks the bridge invokes; specifically,
`EventStreamInitialRequestInterceptor` (gated on an attribute only async event streams set) and
`TraceIdExecutionInterceptor` when `AWS_LAMBDA_FUNCTION_NAME` is unset. On a default DynamoDB client
all three of `awsInterceptors()`'s contributions drop out, the list goes empty, and the lazy install
finally does what it was written to do — `V2InterceptorBridge` is not even class-loaded, verified with
`-verbose:class`. `awssdk.bridge.keepInertInterceptors=true` restores the old behavior, which is what
the new `v2-sync-inert-interceptors` arm sets.

app CPU µs/op against the *filtered* `v2-sync`:

| arm | small-get | small-put | paired wins for the arm |
|---|---:|---:|---:|
| `v2-sync-inert-interceptors` (old behavior) | **+7.4%** | **+8.4%** | 0/4, 0/4 |
| `v2-sync-strip-interceptors` (no v2 interceptors at all) | +0.7% | +0.0% | 2/4, 2/4 |
| `v2-sync-stripped` (`stripAll`) | −4.8% | −6.2% | 4/4, 4/4 |

Three readings, and they agree. Restoring the old behavior costs 7.4%/8.4%, matching the 5.9%/8.4% the
component sweep attributed to this bridge. Stripping interceptors *now* buys nothing — +0.7%/+0.0% with
2/4 wins, i.e. inside the noise — because there is nothing left to strip. And `stripAll` fell from
−13.7%/−13.8% to −4.8%/−6.2%, which is the same total minus the component just removed.

So the **remaining bridging tax on a small operation is ~5–6% of app CPU**, down from ~14%, and the
endpoint bridge is now the largest single piece of it. Correctness is unchanged on the paths that
matter: a customer interceptor overriding a bridged hook still runs (checked directly — a `Live`
interceptor's `modifyHttpRequest` fires once, an `Inert` one overriding only `afterMarshalling` fires
zero times, which is what it did before the filter too). The narrow compatibility exposure is that
inert-ness is judged once at construction from the class and the environment; `compatability_issues.md`
2.1 records it.

This is also the one finding here that generalizes beyond the prototype: it is not a bridging cost at
all but a *bridging-visible* one. The three interceptors run on stock v2 too, doing nothing; the bridge
merely made them expensive enough to notice.

## Streaming: S3 `GetObject` / `PutObject`

Raw data: `pipeline_benchmark2/paired-s3-{8k,256k,8m}/20260905-{2003,2014,2027}/`. An earlier collection
(`…-{1918,1926,1935}`) ran the same six cases with a smaller warmup budget and agrees on every sign and
within ~1.5 points on every magnitude; the later one is quoted because it warmed up longer.

Arms are the same two jars as above (published v2 2.46.10 vs this branch), driven through `S3Client`
with `s3-v2-sync`, path-style addressing, 5 paired reps, concurrency 1. Two conditions differ from the
DynamoDB collection and both are forced:

- **HTTPS, not HTTP.** Over plain HTTP with a request body, `ChecksumUtil.isPayloadSigning` turns
  payload signing back on no matter what `PAYLOAD_SIGNING_ENABLED` says, so stock v2 aws-chunk-signs a
  `PutObject` while the bridge refuses it (13.2). There is no v2 configuration under which an HTTP
  `PutObject` is comparable between the arms, so the mock server serves TLS.
- **Checksums off on both sides** (`WHEN_REQUIRED` for both request calculation and response
  validation). With defaults, the diff would be measuring a bridge feature that is missing (6.1, 12.9)
  at a cost that scales with the object, not measuring the streaming pipeline.

app CPU µs/op, and the absolute saving, which is the interesting column:

| scenario | stock v2 | bridged v2 | delta | saving | pair spread | wins |
|---|---:|---:|---:|---:|---:|---:|
| `get-object-8k` | 164.5 | 110.0 | −33.1% | 54.5 µs | ±1.0% | 5/5 |
| `put-object-8k` | 174.0 | 118.8 | −31.7% | 55.2 µs | ±1.6% | 5/5 |
| `get-object-256k` | 462.6 | 414.2 | −10.5% | 48.4 µs | ±0.5% | 5/5 |
| `put-object-256k` | 567.9 | 499.0 | −12.1% | 68.9 µs | ±1.9% | 5/5 |
| `get-object-8m` | 10,892.2 | 10,795.0 | −0.9% | 97 µs | ±2.8% | 3/5 |
| `put-object-8m` | 12,989.9 | 12,614.1 | −2.9% | 376 µs | ±1.1% | 5/5 |

mean latency µs tells the same story: −26.9%/−27.6% at 8 KiB, −8.1%/−11.3% at 256 KiB, −0.8%/−2.8% at
8 MiB.

**The headline is the saving column, not the percentage.** On `GetObject` the bridge is ~50 µs per call
cheaper regardless of object size — the same fixed amount it saves on a DynamoDB `GetItem`
(136.6 → 92.3 = 44 µs). The percentage collapses from 33% to under 1% purely because the denominator
grows: at 8 MiB a call costs ~11 ms, of which ~50 µs of pipeline is a rounding error. `get-object-8m` at
3/5 wins and ±2.8% is honestly **parity**, and that is the correct result — both arms are sitting on the
same transport moving 8 MiB over TLS at ~700 MB/s, so there is nothing left for a pipeline to win.

The one result that is *not* a fixed offset is `PutObject`, where the saving grows with the object:
55 µs → 69 µs → 376 µs across a 1000× size range, with 5/5 wins and ±1.1% at 8 MiB, so it is not noise.
Backing out the fixed part leaves roughly **0.04 µs per KiB uploaded** in the bridge's favor, worth ~3%
at 8 MiB. The plausible cause is one fewer touch of the buffer on the upload path — smithy's
`DataStream` handing the request body to the transport where v2 walks it through `RequestBody` and its
content-stream wrapper — but that is a hypothesis; an allocation profile of `put-object-8m` on both arms
would settle it and has not been run.

What this does *not* say: nothing here measures multipart, async, or the checksum paths, and with
checksums off the wire is deliberately simpler than a default `S3Client`'s. The streaming
*correctness* results — no buffering in either direction under a heap 4× smaller than the payload,
byte-identical `PutObject`/`UploadPart` requests, and the gaps that remain — are in
`compatability_issues.md` 13; multipart correctness, which does work, and the async gap that keeps it
from being benchmarkable, are in section 14.

## Async: the bridged async client, over CRT and Netty

Raw data: `pipeline_benchmark2/paired-async-c1/merged/` and `pipeline_benchmark2/paired-async-c16/merged/`
(each with `results.csv`, `summary.md`, and a `MERGE.md` explaining the assembly — the collections were
run one rep per invocation because a single 4-rep invocation exceeds the 30-minute background limit the
tooling imposes; arm order alternates between invocations, as it does within a normal run).

| | |
|---|---|
| Arms | `bridge-async-stock-published-2.46.10-dirty.jar` vs `bridge-async-bridge-c1d88972e18-plus-async-wip-dirty.jar`, **same harness commit** |
| Clients | `v2-async` (CRT), `v2-async-netty` (new arm), and `v2-sync` as the control — the sync numbers are the existing result, re-measured |
| Config | 50 000 measured ops, 30 000 warmup, 4 paired reps, client pinned to CPUs 0–1, server to 4–6; concurrency 1 and 16, async driver in `inflight` mode |

**The control reproduces.** `v2-sync` at concurrency 1 comes out at −36/−37/−19/−47% app CPU against the
earlier collection's −32/−34/−19/−43%, on a different day and a rebuilt jar. So the setup is sound, and the
async numbers can be read against the sync ones.

### Concurrency 1: cheaper and faster, by less than sync

| client | small-get | small-put | batch-get | batch-put |
|---|---:|---:|---:|---:|
| **latency** — async, CRT | −16.1% | −16.1% | −9.6% | −41.3% |
| async, Netty | −18.1% | −14.4% | −12.4% | −34.9% |
| sync (control) | −32.5% | −30.5% | −18.1% | −45.0% |
| **app CPU/op** — async, CRT | −11.5% | −13.6% | −4.9% | −41.5% |
| async, Netty | −6.2% | −5.8% | −4.5% | −30.6% |
| sync (control) | −35.9% | −36.6% | −18.7% | −46.9% |

4/4 paired wins in every cell; spread of pairs ±1.4–5.3%. The bridged async client beats stock async on
every scenario and both transports, but on small operations by roughly half of what the bridged sync
client beats stock sync by. Something on the async path costs back part of the pipeline saving. The
per-call candidates are all bridge-side and all new: a virtual-thread start, a hop to the completion
executor, the `FlowAdapters` layers, and — on responses — `ResponseBodyDataStream` copying through v2's
`InputStreamSubscriber` to get around smithy-java's `asByteBuffer` bug (ledger 15.6). **Not profiled;
this is a list of suspects, not an attribution.** Netty's gain is smaller than CRT's on small operations
too, where the response is 470 B, so the difference is not only the large-body copy suspected below;
what else differs by transport is unmeasured.

Caveat: the summary flags 48 of 96 runs (every async case, and sync small ops) as not steady-state — JIT
still compiling inside the window, in **both** arms. Latency and throughput are unaffected; per-op CPU is
the column to hold loosely. The spreads are tight regardless.

### Concurrency 16: throughput, and why latency is not reported

| client | small-get | small-put | batch-get | batch-put |
|---|---:|---:|---:|---:|
| **wall µs/op** (1/throughput) — async, CRT | −23.3% | −28.6% | −12.7% | **−65.4%** |
| async, Netty | −29.1% | −26.1% | −7.4% | **−53.4%** |
| sync (control) | −54.7% | −49.9% | −25.5% | −46.5% |
| **app CPU/op** — async, CRT | −16.9% | −20.9% | −12.1% | −43.0% |
| async, Netty | −21.8% | −25.1% | **+4.9% (0/4)** | −34.0% |
| sync (control) | −53.9% | −49.0% | −21.3% | −44.3% |

**Mean latency is left out on purpose, because at this concurrency it measures the harness, not the
SDK.** The async driver is one submitting thread keeping N calls outstanding (`Driver.java:151-171`).
Stock v2 async marshals and signs *on the caller's thread* before `execute` returns (ledger 16.1), so the
submitter spends that time busy instead of submitting, and never reaches 16 in flight. Little's law says
how far short: stock `v2-async` batch-put runs 940 µs latency at 731 µs/op, i.e. **~1.3 calls in flight**;
the bridge runs 4 027 µs at 253 µs/op, **~15.9**. Stock's latency looks better only because its queue
is shorter, which is also why its throughput is so much worse. The same arithmetic applies, less
extremely, to every async cell.

So the batch-put throughput numbers (−65%, −53%) are real for **this** topology — an application that
submits from one thread, which is common — and overstated for one that submits from many, where stock's
marshalling would spread across callers too. The pipeline-cost number, independent of topology, is app
CPU/op: −12% to −43%, with one loss.

**The loss: Netty batch-get, +4.9%, 0/4**, where CRT batch-get is −12.1%. Batch-get is the one scenario
with a large *response* (~38 KB), and Netty is the transport that delivers it in more, smaller buffers,
so this is consistent with the response-body copy in `ResponseBodyDataStream` above. Consistent with,
not shown to be; an allocation profile of this one cell would settle it. Same steady-state caveat as
concurrency 1, more so: 95 of 96 runs flagged.

### What this means

- Async on the bridge is not a regression anywhere at concurrency 1 and loses in one cell at 16. The
  design — a virtual thread per call over a synchronous pipeline — does not cost more than stock v2's
  `CompletableFuture` pipeline; it costs less, just not as much less as sync.
- The largest async effect is structural, not a pipeline saving: moving pre-transport work off the
  caller's thread lets a single submitter keep its target concurrency. That is the same change that
  costs thread-bound context propagation (ledger 16.1); the two go together.
- Not measured: async S3 streaming and multipart (no async `s3-*` arm yet), and the memory cost of
  queued calls that ledger 15.3 estimates.

## Fidelity cost: what signing with v2's own signer costs

Raw data: `pipeline_benchmark2/paired-fidelity/merged/` (all four scenarios) and
`pipeline_benchmark2/paired-fidelity2/merged/` (small ops, after two trims), each assembled from one-rep
invocations as in the async section. Same conditions: 50 000 ops, 30 000 warmup, 4 paired reps, concurrency 1,
client on CPUs 0–1, server on 4–6, against the same stock jar.

This measures ledger §17 — v2's signer bridged in place of smithy-java's, v2's auth-scheme resolution per
attempt, response hooks, CRC32 validation, request overrides and timeouts — which is what took the fault sweep
from 19 behavioral differences to 1 and every checksum, override and binding probe to parity with stock.

| app CPU/op vs stock | before §17 | after §17 | after trims |
|---|---:|---:|---:|
| sync small-get | −35.9% | −18.5% | **−21.5%** |
| sync small-put | −36.6% | −19.8% | **−19.7%** |
| async small-get | −11.5% | +1.5% | **+2.8%** |
| async small-put | −13.6% | −0.3% | **+1.7%** |
| sync batch-get / batch-put | −18.7% / −46.9% | −13.4% / −44.4% | — |
| async batch-get / batch-put | −4.9% / −41.5% | −2.9% / −36.7% | — |

A fixed ~20 µs per call, so it moves small operations and barely touches batch-put. Latency is still lower
than stock in every cell (sync small −14% to −18%, async small −2% to −3%, 4/4 or 3/4 wins).

**Attribution.** `awssdk.bridge.stripSigner` — smithy-java's signer, no v2 auth-scheme resolution — recovers
all of it on the same jar (sync small-get 108 → 86 µs, small-put 102 → 80 µs, three alternating pairs each).
A JFR profile of the full bridge puts the signing path at 25% of pipeline CPU: v2's `AwsV4HttpSigner` itself
~13%, the request conversions to and from v2's model ~8%, checksum and selected-scheme setup ~2%; the endpoint
bridge's new work (auth-option resolution, the larger attribute copy) another ~5%. The two trims made
afterwards — skipping checksum setup for operations with no checksum metadata, writing back only the headers
signing changed — are inside the noise.

**What it means.** The price of byte-for-byte S3 behavior (checksums, trailers, chunked signing, the
endpoint's signing overrides) is paid on every call, including by DynamoDB, which needs none of it. The
obvious recovery is to sign with smithy-java's signer when v2's would add nothing — no checksum metadata,
default signer properties, no signer override — which would return DynamoDB to its pre-§17 numbers. It is
not done because it rests on a claim not yet proven: that the two signers produce the same signature for
those requests. A fixed-clock signature comparison would settle it.

## Cold start: the bridge's one loss

Raw data: `pipeline_benchmark2/coldstart/20260904-2341/` (60 JVMs, zero failures, `summary.md` from
`analysis/scripts/coldstart_summary.py`). One JVM per data point, `small-get`, 10 reps, arms
interleaved and reversed on even reps. Both jars were rebuilt from the current harness so the only
difference is the SDK. Medians, since each row is one JVM's single first call.

| | baseline v2 | bridged v2 | delta | wins |
|---|---:|---:|---:|---:|
| client construction (ms) | 507 | 603 | **+22.3%** | 0/10 |
| first call (ms) | 192 | 155 | −20.5% | 9/10 |
| **build + first call (ms)** | **693** | **757** | **+10.1%** | 0/10 |
| jvm start → first response (ms) | 1 075 | 1 130 | +5.0% | 1/10 |
| jit at exit (ms) | 822 | 964 | +17.6% | 2/10 |

Caveat 2 predicted this and it is confirmed, with a useful decomposition: the penalty is **entirely in
client construction** (+95 ms), and the bridged client's *first call* is already 20% faster than stock
v2's. Two pipelines' worth of classes have to be loaded and initialized before the first call can
start; after that, the smithy pipeline's speed advantage is present even on call one.

With the bridges stripped, construction is still +18.5% but the first call drops 42.5% (10/10 wins),
netting **+0.4% — break-even**. Native smithy is 600 ms, 13% below stock v2. So the bridged client's
cold-start deficit is not inherent to smithy-java; it is the cost of initializing the v2 builder chain
*and* the smithy pipeline, plus the bridges in between.

For a Lambda or a CLI making a handful of calls, that 64 ms is real and the steady-state win is not
reachable. For anything longer-lived it is amortized within the first few dozen calls: calls 2–5 in the
same JVM are already faster on the bridge (2.9 ms vs 4.6 ms by call 5).

`-verbose:class` on one JVM of each arm locates the extra work: 4 534 classes loaded versus 4 354 (534
bridge-only, 385 no longer needed). The biggest bridge-only groups are the smithy runtime (100
`smithy.java.internal`, 80 `smithy.java.client`, 56 `smithy.java.core`) and — more surprising — **114
classes from the Smithy *model* library** (`smithy.model.shapes`, `smithy.model.traits`), pulled in
because the generated `SCHEMAS` constants build `ShapeId`s and trait objects in static initializers. A
runtime client loading the build-time model library is worth a look on its own; see
`compatability_issues.md` 10.7.

Two null experiments inside this collection: the `smithy` arm is identical code in both jars (−1.0%),
and `v2-sync-stripped` on the baseline jar is the same client as `v2-sync` (+2.9% on build+first). Noise
floor for a 10-JVM median is therefore ~±3%, against a +10.1% effect with 0/10 wins.

## What the timings could not measure: behavior when the service fails

Every number above is from a call that succeeded. That makes the retry strategy and the error enricher
look free, which is true and useless: neither does anything on a successful call. So the two bridged
components with the most surface for silent divergence were the two with no measurement at all.

`error-behavior.sh` closes that. It arms a fault on the mock server, makes one call, and records what the
SDK threw and how many attempts it took — attempt counts from the server's own request counter, not from
anything the SDK reports. There is no averaging and no warmup: each row is a deterministic outcome, and
reps exist only to catch nondeterminism. A difference here is a bug or a ledger entry, not a percentage.

Eleven faults span the axes along which the pipelines can plausibly differ — modeled/unmodeled, retryable
by shape vs by error code vs by status alone, `Retry-After`, modeled-but-not-by-this-operation, unparseable
success, empty 5xx, torn response body, and connection reset — each in a *persistent* variant (every
attempt fails) and a *transient* one (the third attempt would succeed, so a missing retry turns into a
missing result).

### It found a great deal, including one thing nothing else would have

First sweep: **87 behavioral differences.** `internal-error` produced the wrong exception type, and
`unavailable`, `unavailable-retry-after`, `empty-500` and `malformed-body` all returned on the **first**
attempt where v2 made three — in the transient variants, v2 returned the item and the bridge threw. A
working-looking client that does not retry server errors.

Current state, after six further rounds of fix-and-remeasure (`errors/20260905-0255`, the reference run):
**21 of 23 cases match on attempt count and outcome**, with zero rep-to-rep variation.

| Round | Behavioral | Faults | What it established |
|---|---:|---:|---|
| `0138` | 87 | 9 | First sweep, described above |
| `0159` | 19 | 9 | Unmodeled-error and modeled-error enrichment work; `Retry-After` honored (2008 ms vs 2011 ms) |
| `0223` | 14 | 10 | `malformed-body` fixed; found that v2 retries a torn body only via Jackson 2's hierarchy (ledger 3.5) |
| `0230` | 13 | 10 | Fixed an inert fault; **found that streamed bodies mean a torn body never becomes a transport error** |
| `0239` | 20* | 11 | `connection-reset` added: **bridge 1 attempt vs v2's 3**, transient case throws where v2 returns |
| `0246` | 20 | 11 | The obvious fix for that is inert, for a structural reason (below) |
| `0255` | 20 | 11 | Revert verified; reference state for the branch |

\* the rise is the new fault, not a regression — `0239` reproduces every `0230` outcome. Against the
catalogue as it stood at `0138`, the trajectory is 87 → 13.

Counts are `analysis/scripts/error_behavior_diff.py`'s, which each run directory now stores as `diff.md`.
It reports message-text differences **separately** from behavioral ones, because SDKs reword messages
without changing behavior and 14 rows of wording churn would bury the 20 that matter. Adding the two
classes together gives the "34 field differences" figure earlier revisions of this file used; both describe
the same run.

The last two rows are the ones worth the whole exercise. Two faults that both look like "torn connection"
behave completely differently, because bodies are **streamed**: `V2TransportBridge.send` returns as soon
as the response headers arrive, so a truncated body fails inside `ClientPipeline.deserialize` and is
retried correctly, while a connection reset before headers fails inside the transport and is **never
retried at all**. smithy-java drives its entire retry loop from inside `deserialize` — `doSendOrRetry`,
despite the name, has no exception handler — so no exception thrown from a transport, of any type,
reporting any `RetrySafety`, can produce a second attempt. Marking it retryable was implemented and
measured: no change. See `compatability_issues.md` 3.6.

That is the single largest behavioral difference on this branch, it applies to a **native** smithy-java
client and not just a bridged one, and a benchmark that measures latency could not have found it. Nor
would a fault catalogue without that specific fault: it took two faults that appear redundant to separate
the retried case from the unretried one.

### What still differs

The 2 remaining attempt-count differences are both `connection-reset`, which alone accounts for 7 of the 20
behavioral rows — one lost retry moves `attempts`, `outcome`, `exception`, `cause` and `retryable` together.
The other 13 behavioral rows, plus all 14 message differences, are metadata and wording, none of which
changes whether a call is retried:

| Difference | Cases | Ledger |
|---|---|---|
| `awsErrorDetails().rawResponse()` never populated | 10 | 1.4 |
| `(SDK Attempt Count: N)` message suffix absent; two messages lose the service's text | 14 | — |
| `ConditionalCheckFailedException` arrives as `DynamoDbException` | 2 | 1.3 |
| torn-body cause is `SerializationException`, not `UncheckedIOException` | 1 | 3.5 |

Message-text and `rawResponse` differences are cosmetic for control flow but will fail customer tests that
assert on exception messages.

### Caveat

Faults are injected by a mock server, so this covers what a *service* can do to a client. It does not
cover client-side timeouts (`apiCallTimeout`, `apiCallAttemptTimeout`), credential-resolution failure, or
DNS failure, and `connection-reset` reaches the transport path only by proxy for a connect timeout or TLS
failure — the same code, a different `IOException` subtype.

## The cost of retrying

The behavior sweep says the arms fail the same way. It says nothing about what failing *costs*, because
it takes one sample per case under v2's default full-jitter backoff, where a single sample of a throttled
3-attempt call is uniform on roughly `[0, 3 s)`. Two runs with the jitter removed answer two different
questions.

**The configured backoff survives bridging exactly** (`errors/20260905-1527`, `--backoff fixed:200`).
`per extra attempt` is **203.0 ms in every arm and every case** — 200 ms of configured delay plus ~3 ms of
call work — across both a throttling and a non-throttling fault, which take different backoff paths.
No arm-vs-arm difference clears its bootstrap interval, which for this run is the pass condition.

That also disposes of the 4x anomaly previously flagged here. It was jitter, and the proof is structural
rather than statistical: `javap` on `aws-sdkv2-retries-1.6.1.jar` shows `SdkRetryStrategy.refreshRetryToken`
to be pure delegation — it rebuilds a v2 `RefreshRetryTokenRequest` and returns the wrapped v2 strategy's
`delay()` verbatim, as do `acquireInitialToken` and `maxAttempts`. **Delay computation is v2's in both
arms and cannot differ by construction.** The only rewiring is `retryOnException` and `treatAsThrottling`,
and the sweep already shows both arms agreeing on `throttling` for every fault.

**Retry costs the bridge less per attempt, but its advantage is front-loaded**
(`errors/20260905-1532`, `--backoff immediate`, 60 reps, 1,560 rows). With the delay at zero, wall time is
the client's own work: token bookkeeping, classification, and re-running serialization, signing and
endpoint resolution per attempt.

| quantity | `baseline` | `bridge` | ratio |
|---|---:|---:|---:|
| warm 1-attempt call | 1,110 µs | 669 µs | **0.60x** |
| marginal cost of one extra attempt | 675 µs | 578 µs | **0.86x** |
| total, 3-attempt cases | 2,253–2,550 µs | 1,710–1,984 µs | 0.72–0.80x |

A fixed-plus-marginal model predicts the totals to within the noise, which is what makes those two rates
real rather than an artifact of the division: `baseline` 1,110 + 2 x 675 = 2,460 µs against ~2,470
observed; `bridge` 669 + 2 x 578 = 1,825 against ~1,830. So the bridge saves ~441 µs once per execution
and only ~97 µs per attempt — **about a fifth of its per-call advantage recurs on a retry**, and its
relative advantage decays with attempt count.

The leading candidate is the endpoint bridge (3.3), which runs the V2 rules engine per *attempt* rather
than per execution — work that should be once-per-execution being paid per attempt is exactly this shape.
The run measures the aggregate and does not isolate it; memoization is the test, and this is its
before-measurement.

Both readings come from `analysis/scripts/retry_cost_summary.py`, which refuses to run on a
default-backoff sweep so that jitter can never be presented as a measurement. Its statistics are
rank-based (`P(faster)`, bootstrap interval on the median difference) because the samples are
heavy-tailed — one rep reached 44,056 µs against a 1,828 µs median, and a standard-deviation test called
that "indistinguishable" while the bridge led in 13 of 13 cases by 20–40%. All 13 bootstrap intervals
exclude zero; `P(faster)` is 0.65–0.85, which is the honest picture of distributions whose centers are
firmly separated and whose tails overlap.

## Why these numbers can be trusted

Two null experiments ran inside the same collection, both by construction rather than by a separate
run:

- **The `smithy` arm is identical code in both jars** (same smithy-java 1.6.1, same generated client;
  it does not touch the SDK under test). Paired deltas: −0.3%, +9.6%, −2.7%, −0.5% for
  small-get/small-put/batch-get/batch-put.
- **On the baseline jar, `v2-sync-stripped` is the same client as `v2-sync`** (the
  `awssdk.bridge.strip*` properties are unread by an unbridged SDK). Deltas: +1.0%, +0.2%, −3.0%,
  +3.7%.

So the machine's paired resolution here is roughly **±3–4%**, except `smithy`/`small-put`, where one
rep of the four was a 128 µs outlier against a 88–97 µs cluster (46% per-arm spread) and produced the
+9.6% reading. Every v2-sync delta reported above is 18–43% — five to ten times the noise floor — and
won 4/4 pairs in every scenario.

## Caveats that matter

1. **17 of the bridge arm's 24 small-op runs were not steady-state**, versus 2 of the baseline's
   (`steady_state=false`: JIT was still compiling inside the measured window). Warmup itself reported
   settled in 90 of 96 runs — its criterion is 3 s without compilation, and for the bridged client
   that gate is too weak: compilation resumes after the gate opens. So this is a warmup-criterion
   limitation, not a truncated warmup. It biases *against* the bridged arm — its measured window
   includes not-yet-optimized code — so the small-op wins are, if anything, understated. Batch
   scenarios were all steady-state in-window.

   The 6 runs that did hit the 60 s warmup ceiling were all *baseline* `batch-put`. They are not
   distorting that scenario's large margin: having warmed longer (67 500–75 000 ops vs 52 500), they
   came out slightly *faster* than the baseline rep whose warmup settled (714–747 vs 796 µs app CPU),
   against a bridge arm at 419–437.
2. **The bridged client needs about twice the JIT work**: 164–183 ms of compilation on small ops
   versus 81–108 ms for stock v2 (both pipelines' class graphs get loaded and compiled). Steady-state
   throughput is not the whole story for short-lived processes, and the cold-start measurement above
   confirms the prediction that follows from this: +10% to first response, all of it in client
   construction.
3. **GC pressure is lower on the bridged arm** (e.g. small-get 38 ms / 30 collections vs 48 ms / 33),
   consistent with the CPU win being real allocation reduction rather than measurement artifact.
4. **Part of the win is work the bridge does not do.** From `compatability_issues.md`: no response
   metadata or `requestId` parsing (1.4), no metrics timing (7.1), no user-agent business metrics
   (7.2), no `Accept-Encoding: gzip` negotiation (6.3), no CRC32 response validation (6.1). Of these,
   only the first two and the user-agent work are actually exercised by this benchmark — the mock
   server sends no `x-amz-crc32` and does not compress, so those two paths cost stock v2 nothing here
   and are not part of the measured gap. The gap is dominated by pipeline overhead, marshalling and
   signing, not by skipped features, but it is not entirely free of them.
5. Single client thread, loopback, a mock server that returns a fixed body. No real network
   latency, no throttling, no retries actually taken (retry *bookkeeping* is paid by every arm), and no
   TLS except in the S3 streaming collection, where it is unavoidable (see *Streaming*). Failure
   behavior is covered separately and behaviorally rather than as a timing — see *What the timings could
   not measure* — which is where the one severe divergence on this branch turned up.
6. **Every 8 MiB run was flagged non-steady-state**, at both warmup budgets tried (250 and 1000 ops):
   an 8 MiB call is expensive enough that compilation keeps happening inside the window. The paired
   deltas are nonetheless tight (`put-object-8m` ±1.1%, 5/5 wins) because whatever compiles, compiles in
   both arms; but the *absolute* per-op CPU for that band should be read as approximate, and the
   `get-object-8m` parity claim rests on the pairing rather than on either arm's own number.
7. `sdk_commit` reads `published-2` in `results.csv` for the baseline arm — an 11-character
   abbreviation applied to a non-SHA. The jar provenance is correct (`published-2.46.10`) and
   `BuildProvenance.abbreviate` has since been fixed to only abbreviate real SHAs.

  10-attempt configuration should widen it linearly, and that is a sharper test than the memoization
  diff alone.
