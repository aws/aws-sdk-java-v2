# How the smithy-java bridge works

The v2 public API (clients, builders, request/response POJOs, exceptions, `ExecutionInterceptor`,
`ClientOverrideConfiguration`) is unchanged. Underneath, each generated client (sync or async) hands
every call to a single smithy-java `Client`, which owns serialization, endpoint resolution, identity,
retries and deserialization. The bridge (`core/smithy-java-bridge`) adapts the v2 components a customer
configured so smithy-java can drive them. Where v2 behavior lives in a v2 component (the signer,
checksum logic, interceptors), the bridge runs that v2 code instead of reimplementing it.

It is gated per service by the `generateSmithyJavaSerde` customization flag (on for DynamoDB and S3).
`SyncClientClass` and `AsyncClientClass` both read it. Event-stream operations stay on the stock v2
pipeline.

```
DynamoDbClient.getItem(req)              DynamoDbAsyncClient.getItem(req)
  │                                        └─ SmithyBridgeClient.invokeAsync → one virtual thread per call (§7)
  └─ SmithyBridgeClient.invoke(req, GetItemOperation.instance())       // smithy-java Client.call
       ├─ protocol:  AwsJson1Protocol / RestXmlClientProtocol           // serializes req via its $SCHEMA
       ├─ identity:  V2IdentityResolver        → v2 AwsCredentialsProvider
       ├─ endpoint:  V2EndpointResolverBridge  → v2 endpoint provider + v2 auth-scheme provider
       ├─ signing:   V2SigningAuthScheme       → v2 AwsV4HttpSigner (checksums, chunked, UNSIGNED-PAYLOAD)
       ├─ retries:   SdkRetryStrategy.of(v2 RetryStrategy)
       ├─ interceptors: V2ErrorEnricher, V2Crc32Validation, V2InterceptorBridge → v2 ExecutionInterceptors, ...
       └─ transport: V2TransportBridge → v2 SdkHttpClient   |   V2AsyncTransportBridge → v2 SdkAsyncHttpClient
```

Snippets below are trimmed from the DynamoDB and S3 sources generated by the current codegen, and from
the bridge module.

## 1. Client operation method

### The operation body

Stock v2 builds a response handler, an error handler with a `switch` over every error code, a per-request
config copy, and `ClientExecutionParams`, then calls `clientHandler.execute(...)`. On the bridged path all
of that is omitted and the method becomes a single delegation:

```java
// DefaultDynamoDbClient (generated)
@Override
public GetItemResponse getItem(GetItemRequest getItemRequest) throws ... {
    List<MetricPublisher> metricPublishers = resolveMetricPublishers(this.clientConfiguration,
            getItemRequest.overrideConfiguration().orElse(null));
    MetricCollector apiCallMetricCollector = ...;
    try {
        apiCallMetricCollector.reportMetric(CoreMetric.SERVICE_ID, "DynamoDB");
        apiCallMetricCollector.reportMetric(CoreMetric.OPERATION_NAME, "GetItem");
        return smithyClient.invoke(getItemRequest, GetItemOperation.instance());
    } finally {
        metricPublishers.forEach(p -> p.publish(apiCallMetricCollector.collect()));
    }
}
```

`getItemRequest` is passed as-is: the generated POJO already *is* a smithy `SerializableStruct` (section 3).
`GetItemOperation` is a generated smithy `ApiOperation`.

Streaming operations go through `V2StreamingInvoker`, because v2 strips the streaming member from the POJO
and the body has to travel beside the shape, in the per-call `RequestOverrideConfig`:

```java
// DefaultS3Client (generated)
return V2StreamingInvoker.invoke(smithyClient, putObjectRequest, PutObjectOperation.instance(), requestBody);
```

### Building the smithy client (once, in the constructor)

Sync and async constructors emit the same code (`ClientClassUtils.addSmithyClientConstruction`). It
passes in what the bridge can't know on its own:

- the service and the wire protocol
- a lambda that runs the v2 endpoint rules and applies the `@endpoint` host prefix
- the v2 interceptors smithy-java makes redundant
- the base exception type
- a lambda that runs v2's auth-scheme provider, which feeds the signer (section 5)
- the generated per-request config updater, which runs request-level `SdkPlugin`s

The endpoint and auth-scheme providers are read from the call's execution attributes, so a request-level
`overrideConfiguration().endpointProvider(...)` replaces them the way it does on stock v2.

```java
// DefaultDynamoDbClient / DefaultDynamoDbAsyncClient constructor (generated)
this.smithyClient = V2ConfigTranslator.newClientBuilder(
        this.clientConfiguration,
        DynamoDbApiService.instance(),
        new AwsJson1Protocol(DynamoDbApiService.instance().schema().id()),
        (request, executionAttributes) -> V2EndpointResolverBridge.withHostPrefix(
                ((DynamoDbEndpointProvider) executionAttributes.getAttribute(SdkInternalExecutionAttribute.ENDPOINT_PROVIDER))
                        .resolveEndpoint(DynamoDbResolveEndpointInterceptor.ruleParams(request, executionAttributes)).join(),
                DynamoDbResolveEndpointInterceptor.hostPrefix(
                        executionAttributes.getAttribute(SdkExecutionAttribute.OPERATION_NAME), request),
                executionAttributes),
        Set.of(DynamoDbAuthSchemeInterceptor.class, DynamoDbResolveEndpointInterceptor.class,
               DynamoDbRequestSetEndpointInterceptor.class, HttpChecksumValidationInterceptor.class),
        DynamoDbException::builder,
        (request, executionAttributes) -> ((DynamoDbAuthSchemeProvider) executionAttributes
                .getAttribute(SdkInternalExecutionAttribute.AUTH_SCHEME_RESOLVER))
                .resolveAuthScheme(DynamoDbAuthSchemeInterceptor.authSchemeParams(request, executionAttributes)))
    .requestConfigurationUpdater(request -> updateSdkClientConfiguration(request, this.clientConfiguration))
    .build();
```

For bridged services, codegen makes `authSchemeParams` and `hostPrefix` public static so this lambda can
call them. `HttpChecksumValidationInterceptor` goes in the replaced set only when no operation validates
response checksums, which is true for DynamoDB. S3 keeps it, and it runs through the interceptor bridge
(section 6).

`V2ConfigTranslator` reads the v2 `SdkClientConfiguration` once, at construction, and wires each option
into the smithy builder:

```java
builder.service(service)
       .protocol(protocol)
       .transport(transportFor(v2Config))                 // sync or async v2 HTTP client (§4, §7)
       .baseExceptionBuilder(baseExceptionBuilder);
builder.completionExecutor(v2Config.option(SdkAdvancedAsyncClientOption.FUTURE_COMPLETION_EXECUTOR));  // §7
builder.endpointResolver(new V2EndpointResolverBridge(v2Config, endpointResolver, authOptionsResolver));
builder.apiCallTimeout(v2Config.option(SdkClientOption.API_CALL_TIMEOUT));
builder.putConfig(V2Timeouts.CLIENT_ATTEMPT_TIMEOUT, v2Config.option(SdkClientOption.API_CALL_ATTEMPT_TIMEOUT));
builder.putSupportedAuthSchemes(new V2SigningAuthScheme(signingName, signingRegion, clientSigner));   // §5
builder.addIdentityResolver(new V2IdentityResolver(credentialsProvider));                             // §5
builder.addInterceptor(new V2ErrorEnricher(serviceName, baseExceptionBuilder));   // must be first; ledger 3.7
builder.putConfig(V2TransportFailures.ENABLED, Boolean.TRUE);                     // §4
builder.addInterceptor(new V2Crc32Validation(fromCompressed));                    // DynamoDB x-amz-crc32
builder.addInterceptor(V2RestXmlBodyRules.instance());                            // rest-xml only
builder.retryStrategy(SdkRetryStrategy.of(v2RetryStrategy));
builder.addInterceptor(new V2InterceptorBridge(bridgeable, v2Config));            // §6, only if needed
builder.addInterceptor(new V2RequestOverrides.Http(additionalHeaders, userAgentPrefix, userAgentSuffix));
```

`V2ErrorEnricher` must be the first interceptor. In smithy-java 1.6.1, the first interceptor that
doesn't override `modifyBeforeAttemptCompletion` rethrows on the error path, so no interceptor after it
sees the error (ledger 3.7).

### `SmithyBridgeClient.invoke`

A thin subclass of smithy's `Client`. It exposes the protected `call`, applies request-level overrides
and `apiCallTimeout`, and converts smithy exceptions back into v2 ones at the boundary:

```java
public <I extends SerializableStruct, O extends SerializableStruct> O invoke(
        I input, ApiOperation<I, O> operation, Consumer<RequestOverrideConfig.Builder> overrides) {
    try {
        RequestOverrideConfig effective = requestOverrides.apply(input, overrides);
        return V2Timeouts.apiCall(apiCallTimeout(input), () -> call(input, operation, effective));
    } catch (RuntimeException e) {
        throw toV2(e);
    }
}

public RuntimeException toV2(RuntimeException error) {
    if (error instanceof V2ModeledError e)       return e.v2Exception();          // e.g. ConditionalCheckFailedException
    if (error instanceof V2UnmodeledError e)     return e.v2Exception();          // DynamoDbException from the response
    if (error instanceof V2RetryableError e)     return unwrapped(e.original());  // retry-classification carrier
    if (error instanceof V2NonReplayableError e) return unwrapped(e.original());  // "don't re-send this body" carrier
    if (error instanceof CallException e)        return translate(e);             // SdkClientException or base exception
    return error;
}
```

`V2RequestOverrides.apply` turns the request's `overrideConfiguration()` into smithy's per-call config,
and returns `null` when there is none. The request's configuration is stored in the call context under
`V2RequestOverrides.KEY`, and each bridged component reads the field it owns:

| Request override field | Handled by |
|---|---|
| `credentialsProvider` | a per-call `V2IdentityResolver` |
| `plugins` | the generated config updater, then per-call endpoint and identity resolvers |
| `headers`, `rawQueryParameters`, `apiNames` | `V2RequestOverrides.Http`, before signing |
| `endpointProvider`, `authSchemeProvider` | `V2EndpointResolverBridge` |
| `executionAttributes` | `V2EndpointResolverBridge`, `V2InterceptorBridge` |
| `signer` | `V2SignerBridge` |
| `apiCallTimeout`, `apiCallAttemptTimeout` | `V2Timeouts` |

smithy-java has no timeout concept, so `V2Timeouts` builds them the way v2's timeout stages do. A timer
aborts the in-flight HTTP request (each transport registers an abort action per attempt) and interrupts
the waiting thread. The result is then surfaced as v2's `ApiCallTimeoutException` or
`ApiCallAttemptTimeoutException`.

## 2. Input/output translation

Requests and responses aren't copied or wrapped. The generated v2 POJO implements smithy's
`SerializableStruct`, and its `BuilderImpl` implements `ShapeBuilder`, so smithy's codecs read from the v2
request and write into the v2 response builder directly. The generated `ApiOperation` hands the v2 types
to the pipeline:

```java
// operations/GetItemOperation (generated)
public final class GetItemOperation implements ApiOperation<GetItemRequest, GetItemResponse> {
    static final Schema $SCHEMA = Schema.createOperation(ShapeId.from("com.amazonaws.dynamodb#GetItem"));

    @Override public ShapeBuilder<GetItemRequest>  inputBuilder()  { return GetItemRequest.builder(); }
    @Override public ShapeBuilder<GetItemResponse> outputBuilder() { return GetItemResponse.builder(); }
    @Override public Schema inputSchema()  { return GetItemRequest.$SCHEMA; }
    @Override public Schema outputSchema() { return GetItemResponse.$SCHEMA; }
    @Override public List<ShapeId> effectiveAuthSchemes() { return List.of(ShapeId.from("aws.auth#sigv4")); }
    @Override public ApiService service() { return DynamoDbApiService.instance(); }
    ...
}
```

So the input path is `protocol.createRequest(op, getItemRequest, ...)` → `getItemRequest.serializeMembers(serializer)`.
The output path is `GetItemResponse.builder().deserialize(decoder).build()`. What comes back from
`Client.call` is already a `GetItemResponse`.

### Errors are the one place a shim is needed

smithy's error deserializer requires registered error types to extend `ModeledException`, an abstract
class. v2 exceptions already extend `AwsServiceException`, and Java has no multiple inheritance. Each
operation's `TypeRegistry` therefore registers one shared shim, `V2ModeledError`, which delegates
deserialization to the v2 exception's generated builder:

```java
// GetItemOperation (generated). Registers every error the service models, not only GetItem's own,
// because stock v2's per-operation error mapping does the same (GetItem maps ConditionalCheckFailedException).
private static final TypeRegistry TYPE_REGISTRY = TypeRegistry.builder()
        .putType(ResourceNotFoundException.$SCHEMA.id(), V2ModeledError.class,
                 V2ModeledError.builderFactory(ResourceNotFoundException.$SCHEMA, ResourceNotFoundException::builder))
        ...
        .build();

// V2ModeledError.Builder
public ShapeBuilder<V2ModeledError> deserialize(ShapeDeserializer decoder) {
    delegate.deserialize(decoder);          // the v2 exception's own BuilderImpl
    return this;
}
public V2ModeledError build() {
    return new V2ModeledError(schema, (AwsServiceException) delegate.build(), delegate);
}
```

`V2ErrorEnricher` is a smithy interceptor that runs on every attempt:

- Before deserialization, it keeps a copy of any small error body, which becomes `rawResponse()`.
- After deserialization, it fills in `awsErrorDetails`, the status code and the request ID.
- It derives smithy `RetryInfo` from v2's retry classification.

`SmithyBridgeClient` unwraps the shim, so callers catch the concrete v2 type.

### Runtime wrappers (fallback only)

`BridgeStruct` (an `SdkPojo` wrapped as a `SerializableStruct`) and `BridgeOutputBuilder` (a v2 builder
wrapped as a `ShapeBuilder`) do the same job at runtime by walking `SdkField` getters and setters. The generated
clients don't use them. They're kept for the serde benchmarks and as the `SdkPojoDeserializer` fallback
for a nested shape that wasn't generated with the flag.

## 3. Generated model classes

Each model class keeps everything v2 generates (fields, `SDK_FIELDS`, builders, `equals`/`hashCode`)
and adds smithy-java members next to them. `GetItemRequest`, trimmed:

```java
public final class GetItemRequest extends DynamoDbRequest
        implements ToCopyableBuilder<GetItemRequest.Builder, GetItemRequest>, SerializableStruct {

    private static final List<SdkField<?>> SDK_FIELDS = ...;   // unchanged v2 metadata

    // Smithy schema derived from SDK_FIELDS at class-init time; member i == SDK_FIELDS[i].
    public static final Schema $SCHEMA =
            SdkSchemaFactory.structure("com.amazonaws.dynamodb#GetItemInput", SDK_FIELDS);
    private static final Schema SCHEMA_TABLE_NAME = $SCHEMA.member(0);
    private static final Schema SCHEMA_KEY        = $SCHEMA.member(1);
    ...

    @Override public Schema schema() { return $SCHEMA; }

    // Direct field writes, no reflection or per-call lookup: the same shape as a smithy-generated class.
    @Override
    public void serializeMembers(ShapeSerializer serializer) {
        if (this.tableName != null) {
            serializer.writeString(SCHEMA_TABLE_NAME, this.tableName);
        }
        if (this.key != null && !(this.key instanceof SdkAutoConstructMap)) {
            SdkPojoSerializer.writeMap(serializer, SCHEMA_KEY, this.key);   // map<String, AttributeValue>
        }
        if (this.consistentRead != null) {
            serializer.writeBoolean(SCHEMA_CONSISTENT_READ, this.consistentRead);
        }
        ...
    }

    @Override
    public <T> T getMemberValue(Schema member) {
        switch (member.memberIndex()) {
            case 0: return (T) this.tableName;
            case 1: return (T) this.key;
            ...
        }
    }
```

An idempotency-token member is filled at serialization time with the same generator v2 uses. smithy-java
serializes before its retry loop, so every retry sends the same token:

```java
// TransactWriteItemsRequest.serializeMembers (generated)
serializer.writeString(SCHEMA_CLIENT_REQUEST_TOKEN, this.clientRequestToken != null
        ? this.clientRequestToken : IdempotentUtils.getGenerator().get());
```

The builder is the deserialization target:

```java
    static final class BuilderImpl extends DynamoDbRequest.BuilderImpl
            implements Builder, ShapeBuilder<GetItemRequest> {

        @Override
        public ShapeBuilder<GetItemRequest> deserialize(ShapeDeserializer decoder) {
            decoder.readStruct($SCHEMA, this, SmithyMemberConsumer.INSTANCE);
            return this;
        }

        private static final class SmithyMemberConsumer
                implements ShapeDeserializer.StructMemberConsumer<Builder> {
            public void accept(Builder builder, Schema member, ShapeDeserializer de) {
                switch (member.memberIndex()) {
                    case 0: builder.tableName(de.readString(member)); break;
                    case 1: builder.key((Map) SdkPojoDeserializer.readStringMap(member, SDK_FIELDS.get(1), de)); break;
                    case 3: builder.consistentRead(de.readBoolean(member)); break;
                    ...
                }
            }
        }
    }
}
```

`SdkPojoSerializer`/`SdkPojoDeserializer` cover the list and map members that don't fit on one line.
Nested structs (for example `AttributeValue` inside `Key`) are themselves `SerializableStruct`/`ShapeBuilder`,
so the helpers recurse by direct cast.

### Generated operations and service

Two new kinds of class are generated per service, in an `operations` package: one `ApiService`, and one
`ApiOperation` per operation (shown in section 2).

Some operation-level traits live on the call in v2, not on a shape: `httpChecksum`,
`httpChecksumRequired` and `requestCompression`. Operations that have them also implement
`V2OperationMetadata`. That interface writes exactly the execution attributes the stock client method
would, using the same code generators:

```java
// operations/PutObjectOperation (generated)
public final class PutObjectOperation implements V2OperationMetadata<PutObjectRequest>,
        ApiOperation<PutObjectRequest, PutObjectResponse> {

    @Override
    public void putExecutionAttributes(PutObjectRequest putObjectRequest, V2OperationMetadata.Attributes attributes) {
        attributes.putExecutionAttribute(SdkInternalExecutionAttribute.HTTP_CHECKSUM,
                HttpChecksum.builder().requestChecksumRequired(false).isRequestStreaming(true)
                        .requestAlgorithm(putObjectRequest.checksumAlgorithmAsString())
                        .requestAlgorithmHeader("x-amz-sdk-checksum-algorithm").build());
    }
    ...
}
```

`V2EndpointResolverBridge` calls it once per attempt. The resulting attributes reach v2's signer and v2's
response-checksum interceptor (sections 5 and 6).

### Where the schema's traits come from

The schema is built from C2J `SdkField` metadata, not from a Smithy model. `SdkSchemaFactory` maps v2's
`LocationTrait`/`PayloadTrait`/`ListTrait`/`MapTrait`/`TimestampFormatTrait` onto smithy binding traits
so smithy's HTTP binding codecs route each member correctly:

```java
switch (location) {
    case PATH, GREEDY_PATH -> traits.add(new HttpLabelTrait());
    case HEADER            -> traits.add(field.marshallingType() == MarshallingType.MAP
                                  ? new HttpPrefixHeadersTrait(wireName)     // x-amz-meta-*
                                  : new HttpHeaderTrait(wireName));
    case QUERY_PARAM       -> traits.add(new HttpQueryTrait(wireName));
    case PAYLOAD           -> isBodyMember = true;                           // ordinary body member
    default -> throw new IllegalStateException("unmapped MarshallLocation " + location);
}
if (field.getTrait(PayloadTrait.class) != null) traits.add(new HttpPayloadTrait());
if (listTrait != null && listTrait.isFlattened())  traits.add(new XmlFlattenedTrait());
// + JsonNameTrait/XmlNameTrait for divergent wire names, TimestampFormatTrait
```

This reconstruction is the weakest part of the design. C2J has already flattened some traits away, so
the factory has to infer them. Five silent wire bugs in S3 (ledger §12) came from exactly this. See
`alexwoo-smithy-java-runtime.md` §4.

## 4. HTTP client translation

`V2ConfigTranslator.transportFor` picks the transport from whichever HTTP client the v2 config carries. A
sync builder sets `SYNC_HTTP_CLIENT`, and an async builder sets `ASYNC_HTTP_CLIENT`, which selects
`V2AsyncTransportBridge` (section 7).

`V2TransportBridge` implements smithy's `ClientTransport<HttpRequest, HttpResponse>` over the customer's
v2 `SdkHttpClient`. Any v2 sync HTTP client (Apache, Apache5, URLConnection, CRT) works unchanged.
Bodies are streamed in both directions, never buffered:

```java
public final class V2TransportBridge implements ClientTransport<HttpRequest, HttpResponse> {
    private final SdkHttpClient v2HttpClient;

    @Override
    public HttpResponse send(Context context, HttpRequest request) {
        try {
            return V2Timeouts.attempt(V2Timeouts.attemptTimeout(context), () -> sendAttempt(request));
        } catch (RuntimeException e) {
            return V2TransportFailures.defer(context, e);    // into the retry loop, see below
        }
    }

    private HttpResponse sendAttempt(HttpRequest request) {
        ExecutableHttpRequest executable = v2HttpClient.prepareRequest(toV2Request(request));
        V2Timeouts.registerAbort(executable::abort);         // what a timeout calls to release the connection
        return toSmithyResponse(executable.call());
    }

    private static HttpExecuteRequest toV2Request(HttpRequest request) {
        SdkHttpFullRequest.Builder b = SdkHttpFullRequest.builder()
                .uri(request.uri().toURI())
                .method(SdkHttpMethod.fromValue(request.method()));
        request.headers().map().forEach(b::putHeader);
        // Replayable DataStream -> re-openable ContentStreamProvider, so v2 can resend it.
        ContentStreamProvider body = request.body().isReplayable()
                ? ContentStreamProvider.fromInputStreamSupplier(request.body()::asInputStream)
                : ContentStreamProvider.fromInputStream(request.body().asInputStream());
        ...
    }

    private static HttpResponse toSmithyResponse(HttpExecuteResponse v2Response) {
        DataStream body = v2Response.responseBody()
                .map(in -> DataStream.ofInputStream(in, null, -1))   // v2 stream handed straight through
                .orElse(DataStream.ofBytes(new byte[0]));
        return HttpResponse.of(HttpVersion.HTTP_1_1, v2Response.httpResponse().statusCode(),
                               HttpHeaders.of(v2Response.httpResponse().headers()), body);
    }
}
```

### Transport failures are deferred into the retry loop

smithy-java 1.6.1 decides retries inside `ClientPipeline.deserialize`. So a failure thrown from `send`
(connection refused or reset, TLS failure, attempt timeout) was never retried (ledger 3.6). v2 retries
all of these.

Both transport bridges now avoid that by not throwing:

1. The transport records the failure against the attempt in the call context.
2. It returns a marked stand-in response (status 599, header `x-smithy-bridge-deferred-transport-failure`).
3. Deserialization turns that response into an attempt error, the same way it handles any failed
   response, so the error goes through the retry decision.
4. `V2ErrorEnricher` recognizes the marker, swaps the real failure back in, and classifies it as v2 would.

```java
// V2TransportFailures.defer
context.put(KEY, new Deferred(attempt(context), failure));
return HttpResponse.of(HttpVersion.HTTP_1_1, 599, HttpHeaders.of(Map.of(MARKER, List.of("1"))), DataStream.ofEmpty());

// V2ErrorEnricher.classify
RuntimeException deferred = V2TransportFailures.deferredFailure(hook.context());
if (deferred != null && V2TransportFailures.isStandIn(hook.response())) {
    if (retriedByV2(deferred, false)) {
        throw new V2RetryableError(deferred);
    }
    throw deferred;
}
```

The response-side bridges skip the stand-in, and the caller only ever sees the original exception. This
is a workaround; the real fix is an upstream change in `ClientPipeline`.

`SmithyTransportSdkHttpClient` goes the other way: it wraps a smithy `ClientTransport` as a v2
`SdkHttpClient`, so a stock v2 client can run over smithy-java's HTTP client.

## 5. Credentials, identity and signing

### Identity

v2's credential providers (profile, SSO, IMDS, container, web identity, STS, with their caching and
refresh) are kept, not replaced. `V2IdentityResolver` adapts the v2 `IdentityProvider` to smithy's
`IdentityResolver`, and it wraps the v2 identity as a view rather than copying it:

```java
public final class V2IdentityResolver
        implements IdentityResolver<software.amazon.smithy.java.aws.auth.api.identity.AwsCredentialsIdentity> {

    private final IdentityProvider<? extends AwsCredentialsIdentity> v2Provider;

    @Override
    public IdentityResult<...AwsCredentialsIdentity> resolveIdentity(Context requestProperties) {
        AwsCredentialsIdentity v2Identity = CompletableFutureUtils.joinLikeSync(v2Provider.resolveIdentity());
        return IdentityResult.of(new SmithyCredentialsAdapter(v2Identity));
    }

    private static final class SmithyCredentialsAdapter implements ...AwsCredentialsIdentity {
        private final AwsCredentialsIdentity v2;
        public String accessKeyId()     { return v2.accessKeyId(); }
        public String secretAccessKey() { return v2.secretAccessKey(); }
        public String sessionToken()    { return v2 instanceof AwsSessionCredentialsIdentity s ? s.sessionToken() : null; }
        public String accountId()       { return v2.accountId().orElse(null); }
    }
}
```

A request-level `credentialsProvider` replaces the resolver for that one call (`V2RequestOverrides`).
`V2IdentityResolver.toV2` unwraps the adapter wherever v2 code needs the v2 identity back: the endpoint
rules (for the `AccountId` builtin) and the signer.

### Signing with v2's signer

Much of S3's wire behavior lives in v2's `AwsV4HttpSigner`, driven by signer properties that v2's
auth-scheme provider resolves per operation:

- flexible checksums, sent as a header or as an `aws-chunked` trailer
- chunked signing over plain HTTP
- `UNSIGNED-PAYLOAD` over HTTPS
- `DOUBLE_URL_ENCODE` and `NORMALIZE_PATH`

smithy-java 1.6.1's `SigV4Signer` implements none of these. So `V2SigningAuthScheme` registers as
smithy's `aws.auth#sigv4` scheme and signs with v2's signer, through `V2SignerBridge`. Identity, endpoint
resolution, retries and serde stay smithy-java's.

The signer's inputs are assembled in `V2EndpointResolverBridge`. That's the one place that already builds
v2 execution attributes per attempt with the input in hand, and it runs before signing. It:

1. writes the operation's `V2OperationMetadata` (checksum traits) into those attributes;
2. resolves v2's auth-scheme options with v2's own provider, keeping the SigV4 option;
3. layers the endpoint rule's signing properties on top, so S3 access points and Outposts sign for the
   right scope;
4. attaches the result to the resolved endpoint.

```java
// V2EndpointResolverBridge.resolveEndpoint (per attempt)
putOperationMetadata(params, attributes);                          // V2OperationMetadata.putExecutionAttributes
software.amazon.awssdk.endpoints.Endpoint v2Endpoint = v2Resolver.resolve(input, attributes);
return Endpoint.builder()
        .uri(v2Endpoint.url())
        .putProperty(V2SigningAuthScheme.SIGNING_INPUTS, new V2SigningAuthScheme.SigningInputs(
                withEndpointSignerProperties(sigV4Option(input, attributes), v2Endpoint), attributes))
        .build();
```

The signer reads those inputs back from `CallContext.ENDPOINT`. It runs v2's own checksum decision
(`HttpChecksumUtils`, `HttpChecksumResolver`), and then v2's signer:

```java
// V2SignerBridge.sign
AuthSchemeOption option = resolveOption(properties, v2Request, v2Identity);  // v2 checksum-spec resolution
if (overrides != null && overrides.signer().isPresent()) {
    return new SignResult<>(signLegacy(..., overrides.signer().get()));        // request-level legacy Signer
}
if (body instanceof V2DataStreams.AsyncBody asyncBody) {
    return new SignResult<>(signAsync(request, v2Request, v2Identity, option, asyncBody));   // §7
}
return new SignResult<>(signSync(request, v2Request, v2Identity, option, body));

// signSync
SignRequest.Builder<AwsCredentialsIdentity> signRequest =
        SignRequest.builder(v2Identity).request(v2Request.build()).payload(payload);
option.forEachSignerProperty(signRequest::putProperty);
SignedRequest signed = v2Signer.sign(signRequest.build());
// headers the signer added (Authorization, X-Amz-Date, x-amz-content-sha256, checksum/trailer framing)
// and any re-framed payload are copied back onto the smithy request
```

Operations without checksum metadata (every DynamoDB operation) skip the checksum resolution entirely.
If the endpoint bridge is stripped or no auth-options resolver is supplied, the translator falls back to
smithy's own `SigV4AuthScheme`.

Two limits:

- Generated operations still declare only `aws.auth#sigv4`.
- The endpoint bridge takes only v2's SigV4 option. SigV4a and S3 Express session auth are skipped, and a
  call fails if the provider offers no SigV4 option.

## 6. Interceptor translation

`V2InterceptorBridge` is one smithy `ClientInterceptor` that runs the whole v2 `ExecutionInterceptor`
chain through v2's own `ExecutionInterceptorChain`, so v2's ordering and result validation are kept.
Thirteen of v2's eighteen hooks are bridged, onto six smithy hooks:

| smithy `ClientInterceptor` | v2 `ExecutionInterceptor` |
|---|---|
| `readBeforeExecution` | `beforeExecution` |
| `modifyBeforeSerialization` | `modifyRequest` |
| `modifyBeforeSigning` | `modifyHttpRequest` / `modifyHttpContent` |
| `modifyBeforeDeserialization` | `afterTransmission`, `modifyHttpResponse`, `modifyHttpResponseContent` / `modifyAsyncHttpResponseContent`, `beforeUnmarshalling` |
| `modifyBeforeCompletion` | `afterUnmarshalling`, `modifyResponse` |
| `readAfterExecution` | `afterExecution` / `onExecutionFailure` |

`modifyHttpRequest` maps to `modifyBeforeSigning` so that headers it adds get signed, as in v2. The v2
`InterceptorContext` and `ExecutionAttributes` are carried across hooks in smithy's call context, and a
request's own `executionAttributes()` are merged in at `readBeforeExecution`:

```java
@Override
public <I extends SerializableStruct> I modifyBeforeSerialization(InputHook<I, ?> hook) {
    CallState state = hook.context().get(STATE);
    InterceptorContext result = chain.modifyRequest(state.context, state.attributes);
    state.context = result;
    SdkRequest modified = result.request();
    // The v2 request IS the smithy input, so a swapped request goes straight back in.
    return modified == hook.input() ? hook.input() : hook.asInputType((SerializableStruct) modified);
}

@Override
public <RequestT> RequestT modifyBeforeSigning(RequestHook<?, ?, RequestT> hook) {
    SdkHttpRequest before = toV2Request((HttpRequest) hook.request());      // smithy -> v2
    state.context = state.context.copy(b -> b.httpRequest(before));
    SdkHttpRequest after = chain.modifyHttpRequestAndHttpContent(state.context, state.attributes).httpRequest();
    if (after == before) return hook.request();
    ModifiableHttpRequest m = ((HttpRequest) hook.request()).toModifiable(); // v2 -> smithy
    m.setMethod(after.method().name());
    m.setUri(writeBackUri(after));
    m.setHeaders(after.headers());
    return hook.asRequestType(m);
}
```

The response hooks are where v2's own behavior lives. Every v2 client carries
`HttpChecksumValidationInterceptor`, and S3 adds trailing-MD5 stripping and URL-decoding of listing keys.
The bridge hands the response body to the chain in the form the client type expects: an `InputStream`
for sync, a publisher for async. Whatever the chain returns becomes the body smithy deserializes, or the
body a streaming caller reads, so a validating wrapper sits where v2 puts it:

```java
@Override
public <ResponseT> ResponseT modifyBeforeDeserialization(ResponseHook<?, ?, ?, ResponseT> hook) {
    if (... || V2TransportFailures.isStandIn(response)) return hook.response();   // no hooks for a failed send
    adoptSigningAttributes(hook.context(), state);    // the attempt's checksum spec, from the signer inputs
    boolean async = state.attributes.getAttribute(SdkExecutionAttribute.CLIENT_TYPE) == ClientType.ASYNC;
    InputStream in = async ? null : body.asInputStream();
    Publisher<ByteBuffer> publisher = async ? FlowAdapters.toPublisher(body) : null;

    state.context = state.context.copy(b -> b.httpResponse(v2Response).responseBody(in).responsePublisher(publisher));
    chain.afterTransmission(state.context, state.attributes);
    InterceptorContext result = chain.modifyHttpResponse(state.context, state.attributes);
    if (async) result = chain.modifyAsyncHttpResponse(result, state.attributes);
    chain.beforeUnmarshalling(result, state.attributes);
    // re-wrap result.responseBody() / result.responsePublisher() as the DataStream smithy will read
    ...
}
```

`V2ConfigTranslator` decides which interceptors go into the chain, and installs the bridge only if at
least one is left:

- The generated auth-scheme and endpoint interceptors are dropped. smithy-java does their work, and
  running them would resolve things nothing reads.
- `HttpChecksumValidationInterceptor` is dropped when the service has no response-validating operation.
- Provably inert interceptors are dropped: any that override none of the bridged hooks,
  `EventStreamInitialRequestInterceptor`, and `TraceIdExecutionInterceptor` outside Lambda.

```java
List<ExecutionInterceptor> bridgeable = bridgeableInterceptors(v2Config, replacedInterceptors);
if (!bridgeable.isEmpty()) {
    builder.addInterceptor(new V2InterceptorBridge(bridgeable, v2Config));
}
```

On a default DynamoDB client nothing survives the filter, so `V2InterceptorBridge` is never installed.
That filter recovered 6–8% of app CPU on small operations.

Known gaps (ledger 2.1):

- These five hooks still aren't bridged: `beforeMarshalling`, `afterMarshalling`,
  `modifyAsyncHttpContent`, `beforeTransmission` and `modifyException`. `modifyException` is why S3's
  exception translation doesn't run.
- A body swapped in by `modifyHttpContent` is dropped.
- In `modifyHttpRequest`, interceptors see the client endpoint rather than the resolved one, because
  smithy resolves the endpoint after this hook.

## 7. Async clients

smithy-java 1.6.1 has no async API: `Client.call`, `ClientPipeline.send` and `ClientTransport.send` all
return their result. The async client therefore shares the sync client's whole pipeline, including the
same smithy `Client`, config translation and bridges. Only two pieces are async-specific, and neither is
in smithy-java:

- **The envelope.** Each call runs the blocking `Client.call` on its own virtual thread and completes a
  v2-shaped `CompletableFuture`.
- **The transport and bodies.** `V2AsyncTransportBridge` drives v2's Netty or CRT client and returns as
  soon as response headers arrive. Request and response bodies stay reactive publishers, so bytes move on
  the event loops and nothing is buffered.

A call therefore holds a parked virtual thread from dispatch until headers arrive, and no platform
thread. The JFR pinning check over the async suites found 0 of 458 virtual threads pinned (ledger 16).

### The generated async method

```java
// DefaultDynamoDbAsyncClient (generated)
@Override
public CompletableFuture<GetItemResponse> getItem(GetItemRequest getItemRequest) {
    List<MetricPublisher> metricPublishers = ...;
    MetricCollector apiCallMetricCollector = ...;
    try {
        apiCallMetricCollector.reportMetric(CoreMetric.SERVICE_ID, "DynamoDB");
        apiCallMetricCollector.reportMetric(CoreMetric.OPERATION_NAME, "GetItem");
        CompletableFuture<GetItemResponse> executeFuture =
                smithyClient.invokeAsync(getItemRequest, GetItemOperation.instance());
        CompletableFuture<GetItemResponse> whenCompleted = executeFuture.whenComplete((r, e) ->
                metricPublishers.forEach(p -> p.publish(apiCallMetricCollector.collect())));
        return CompletableFutureUtils.forwardExceptionTo(whenCompleted, executeFuture);   // cancel forwarding
    } catch (Throwable t) {
        metricPublishers.forEach(p -> p.publish(apiCallMetricCollector.collect()));
        return CompletableFutureUtils.failedFuture(t);    // never throws synchronously
    }
}
```

Streaming operations use `V2AsyncStreamingInvoker` instead:

```java
// DefaultS3AsyncClient (generated)
CompletableFuture<ReturnT> executeFuture = V2AsyncStreamingInvoker.invoke(smithyClient, getObjectRequest,
        GetObjectOperation.instance(), null, asyncResponseTransformer);
CompletableFuture<PutObjectResponse> executeFuture = V2AsyncStreamingInvoker.invoke(smithyClient, putObjectRequest,
        PutObjectOperation.instance(), requestBody);
```

For S3, that covers 105 of 106 async operations. `SelectObjectContent` is an event stream, so it keeps
the stock body and runs through v2's `clientHandler` in the same client.

### The envelope: `SmithyBridgeClient.runAsync`

```java
private static final ThreadFactory ENVELOPE_THREADS =
        Thread.ofVirtual().name("sdk-smithy-bridge-call-", 0).factory();

public <I extends SerializableStruct, O extends SerializableStruct> CompletableFuture<O> invokeAsync(
        I input, ApiOperation<I, O> operation, Consumer<RequestOverrideConfig.Builder> overrides) {
    return runAsync(() -> CompletableFuture.completedFuture(invoke(input, operation, overrides)));
}

public <T> CompletableFuture<T> runAsync(Supplier<CompletableFuture<T>> body) {
    CompletableFuture<T> result = new CompletableFuture<>();
    try {
        ENVELOPE_THREADS.newThread(() -> {
            CompletableFuture<T> produced;
            try {
                produced = body.get();                     // the whole blocking call, incl. v2 error translation
            } catch (Throwable t) {
                completeOnCompletionExecutor(result, null, t);
                return;
            }
            produced.whenComplete((value, error) -> completeOnCompletionExecutor(result, value, error));
        }).start();
    } catch (RuntimeException e) {
        result.completeExceptionally(asCompletionException(e));
    }
    return result;
}
```

Three v2 behaviors are matched on purpose:

- Futures complete on the configured `FUTURE_COMPLETION_EXECUTOR`. If that executor rejects the task,
  the future completes inline.
- A failure is a `CompletionException` whose cause is the v2 exception.
- Nothing throws from the call site.

Because the envelope runs the sync `invoke`, `apiCallTimeout` covers the async path too: the thread it
interrupts is the envelope.

### The async transport: `V2AsyncTransportBridge`

`send` keeps smithy's synchronous contract, but it only parks to wait. It calls v2's
`SdkAsyncHttpClient.execute`, then waits on a future that `onStream` completes with the headers and the
body publisher:

```java
private HttpResponse sendAttempt(HttpRequest request) {
    ResponseSignal signal = new ResponseSignal();                  // an SdkAsyncHttpResponseHandler
    SdkHttpContentPublisher contentPublisher = toContentPublisher(request.body());
    CompletableFuture<Void> exchange = v2HttpClient.execute(AsyncExecuteRequest.builder()
            .request(toV2Request(request, contentPublisher))       // adds Transfer-Encoding: chunked if length unknown
            .requestContentPublisher(contentPublisher)
            .responseHandler(signal)
            .build());
    exchange.whenComplete((ignored, error) -> signal.exchangeCompleted(error));  // never park forever
    V2Timeouts.registerAbort(() -> exchange.cancel(true));        // how a timeout aborts an async exchange
    return signal.awaitResponse();                                 // parks the virtual thread until headers
}

// ResponseSignal
public void onHeaders(SdkHttpResponse headers) { this.headers = headers; }
public void onStream(Publisher<ByteBuffer> body) {
    response.complete(HttpResponse.of(HttpVersion.HTTP_1_1, headers.statusCode(),
            HttpHeaders.of(headers.headers()), new ResponseBodyDataStream(body, contentType, contentLength)));
}
```

The request body needs no byte adaptation. A smithy `DataStream` is already a `Flow.Publisher<ByteBuffer>`,
so `FlowAdapters.toPublisher` exposes it as the reactive-streams publisher v2 expects. An unknown length
is reported as empty, which is what makes `addFraming` send chunked. Neither Netty nor CRT frames an
unknown-length body on its own; without this header the body is silently lost (ledger 15.1).

The response body is a `ResponseBodyDataStream` over the transport's publisher, not
`DataStream.ofPublisher`. smithy-java 1.6.1's publisher-backed stream throws on its first
`asByteBuffer()`, and that's how the codecs read every non-streaming response (ledger 15.6). Send
failures are deferred into the retry loop exactly as in the sync bridge (section 4).

### Streaming bodies: `V2DataStreams` and `V2AsyncStreamingInvoker`

Both directions are interface adaptation only, with no extra thread and no copy:

```java
// AsyncRequestBody -> DataStream, keeping the v2 body reachable for the signer
public static DataStream toDataStream(AsyncRequestBody body) {
    return new AsyncBody(body, isReplayable(body));    // subscribe() -> body.subscribe(FlowAdapters.toSubscriber(s))
}

// DataStream -> what an AsyncResponseTransformer consumes
public static SdkPublisher<ByteBuffer> toSdkPublisher(DataStream body) {
    return SdkPublisher.adapt(FlowAdapters.toPublisher(body));
}
```

`V2AsyncStreamingInvoker` drives the caller's `AsyncResponseTransformer` in v2's order, inside the
envelope:

```java
return client.runAsync(() -> {
    AtomicReference<DataStream> sink = new AtomicReference<>();
    Consumer<RequestOverrideConfig.Builder> overrides = body == null
            ? V2StreamingBridge.forResponseBody(sink)
            : V2StreamingBridge.forBoth(V2DataStreams.toDataStream(body), sink);
    CompletableFuture<ReturnT> transformed = transformer.prepare();
    O response;
    try {
        response = client.invoke(input, operation, overrides);
    } catch (RuntimeException e) {
        transformer.exceptionOccurred(e);              // lets toFile() delete a partial file
        throw e;
    }
    transformer.onResponse(response);
    transformer.onStream(V2DataStreams.toSdkPublisher(sink.get() == null ? DataStream.ofEmpty() : sink.get()));
    return transformed;                                // envelope exits; the caller drains the event loop
});
```

The same bridges handle async bodies in their own form:

- **Signing.** `V2SignerBridge` sees an `AsyncBody` and calls v2's `signAsync`. That frames a checksum
  trailer by wrapping the publisher, so the body never becomes a blocking stream.
- **Interceptors.** `V2InterceptorBridge` hands response interceptors a publisher rather than an
  `InputStream`.
- **Retries.** smithy's own retry guard only checks modeled stream members, so it can't see a one-shot
  body passed beside the shape. When the body isn't replayable, `V2ErrorEnricher` wraps the failure in
  `V2NonReplayableError`, and the call fails with the real error instead of re-sending (ledger 16.4).

### Where async differs from stock (ledger 16)

- **Work before the transport runs on the envelope thread, not the caller's.** This covers
  `beforeExecution`, marshalling, and endpoint and credential resolution. It helps callers on event loops,
  but interceptors that read a `ThreadLocal` (MDC, tracing context) see the envelope's empty value.
- **`AsyncResponseTransformer.prepare()` runs once per call, not once per attempt.** smithy's retry loop
  isn't reachable from outside `Client.call`.
- **Cancelling the returned future doesn't stop the call.** It fails the future, but the envelope keeps
  running and the v2 exchange isn't aborted. Timeouts do abort the exchange.
- **Performance.** For DynamoDB at concurrency 1, the bridged async client measured 4–42% cheaper in app
  CPU than stock async, about half the sync client's margin.
